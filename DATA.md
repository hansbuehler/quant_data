# Data Principles

Here are proposed principles for data handling in ***quantdata**.

When speaking about data we face the following challenges:

1) **All Data**

    * **Lazy Caching**: As long as space permits, caching is a method to speed up model development as it avoid having to re-compute data sets many times.
      Therefore, a core tennent of **quantdata** is an intergated caching system for most data.<br>
      Caching has two main requirements:

      **Parameter-controlled:**<br>
      Nearly all data sets are parameterized (e.g. select all quotes with positive sizes and prices). Such parameters generate 
      a unique function call key which is used to differentiate different data sets defined by different parameter sets.
      The risk with this approach is that while developing you are using many different parameter settings - whose files then pile up on your disk.
      *There is no systematic clean up process yet in place. You will need to delete old, unused files yourself.*

      A good practise for identifying a data set via its function parameters is the use of [``@dataclass``](https://docs.python.org/3/library/dataclasses.html).
      - Create a class for your particular use case. 
        See an example such as ``ExpiryFilter`` in ``qauntdata/widb/day.py`.
      - Create a ``__str__`` which provides a *very compressed* summary of your config. It is helpful to print such information out before any major processing  
        so one can catch if any settings are off early on.
      - When decorating your function for caching, use both the identifying string and the object to create a unique ID to store the data under.
        See ``enrich_day()`` in ``qauntdata/widb/day.py`` as an example. Do not ID any function by the content of numpy/panda/polar data, but
        by the generating parameter set. That can become a bit tedious because it means providing all generating configs for higher level functions.

      **Version-aware:** code changes over time.<br>
      Some code changes such as bug fixes logically require a re-calculation of the affected data sets.
      This is controlled by versioning chached functions, including providing information on dependent function calls: if a function  ``f`` calls
      a function ``g`` whose version has changed, then data generated by ``f`` must be updated, too.
  
      The drawback of this automated update mechanism is that a change in version which we pull from git can suddenly trigger a major re-run of
      our pipeline. This can be very tedious, in particular if we are in the middle of on-going experimentation.
      *There is currently no protection against a git-pull re-pipelining event. You will need to make sure you only pull if you either know
      the state of any version updates, or when you have the time run an update.*
        
      Caching in  **quantdata** is implemented using [`cdxcore.subdir.SubDir.cache](https://quantitative-research.de/docs/cdxcore/api/generated/cdxcore.subdir.html#cdxcore.subdir.SubDir.cache) which provides a framework for caching functions automatically based on their function parameters.

      **Testing**:<br>
      integration tests should not access any connectivity end point. For this reason **quantdata** turns off testing at the root in testing.
      You should store data sets you need for intergation testing in ``tests/stored_data``. 

      **User Friendl:**<br>
      Each piece of a data pipeline should have an associated small self-contained example notebook in the respective ``notebooks/`` directory.

2) **Raw data** by which we mean data downloaded from a vendor. 

   In most cases we will want to cache any data we donwloaded because connections tend to be slow, and we may iterate over the same data many times.
   The component which handles data access should provide default connection management and clear actionable error messages if a connection cannot
   be established.

   Key points regarding data:

   * Store raw data as closs as possible to what you downloaded. Do few if any data transformations.
   * This data typically changes little once the first full version of a connector is published.
   * It should be possible to share this data e.g. via a shared drive provided each consumer has the correct license.
   * Do not connect to the data provider if the data is already cached on disk.

2) **Processed data** by which we mean common transformation of raw data.

   This data includes cleaning data and filtering data.
   As discussed above, such processing should be controlled by configuration ``dataclasses``. 

   Further key points:

   * Do not establish a connection to underlying raw data if the raw data has already been cached. Apart from being good practise, this will also make sure your code works in testing.
   * Split the procesing pipeline in meaningful steps, each of which is likely useful on its own. Typicals steps:
     - Remove obviously wrong data from the raw data set; re-arrange data in a more convenient format; implement natural sorting (e.g. in time). Typically this "first line" processor
       has few parameters and should be fairly universal.
     - Filter data based on market parameters. Provide very common analytics where likely useful for example implied volatilties. Avoid heavy computations.
     - Towards specific use cases, for example finding arbitrage-free mids, or other more specific applications.
   * Use parallel processing to mass-process data more quickly.
     See the pattern used in ``WIDB/timeseries.py`` on how to use features from the caching framework to:
     - Create a list of all data files requested.
     - Identify and do not re-compute (unless specifically requested) files which are already present and have the correct version.
     - Run those files which are missing/have the wrong version.

3) **Benchmark/Training data**

   Such data sets tend to be defined by the model family being trained. They are typically not easily re-usable. Instead, they serve as benchmarks for improvements
   in the respective experiment. In the future models/benchmarks will live outside **quantdata** each in their own git repository.
