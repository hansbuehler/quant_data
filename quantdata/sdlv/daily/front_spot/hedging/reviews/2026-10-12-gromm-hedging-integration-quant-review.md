# GROMM Hedging Integration Quant Review

**Date:** 2026-10-12
**Verdict:** **FAIL**
**Scope:** the dated rolling GROMM2 daily/weekly adapters, common GROMM
objectives/training/hedger, relevant tests, and the corresponding README/PLAN
claims. Implementation files were not modified.

## Blocking findings

### 1. Generated hedge returns are not anchored to the common executable entry marks

The daily generator prices the hedge options from the fitted GROMM2 state in
`gromm2_daily.py:256` and constructs option gains relative to those model prices
in `gromm2_daily.py:374`. The realized benchmark instead executes and evaluates
the same contracts from their released SANOS marks in
`benchmark/digital_daily.py:251` and `benchmark/digital_daily.py:308`. The
difference is a deterministic position-dependent P&L shift, so it changes every
mean-sensitive objective and can create or remove apparent profitable hedge
directions.

The weekly path has the same issue. Its time-zero generated marks come from
`_price_options` in `gromm2_weekly.py:105`, while the live action feature uses the
common marks in `gromm2_weekly.py:490`. In the current synthetic weekly fixture,
the generated and live features for the identical initial decision differ in ten
option-mark coordinates, with maximum absolute difference
`0.029819200401724744`. The differing coordinates are 23--32. By comparison,
the shared generated-model implementation deliberately starts at the executable
marks in `models/generated_weekly.py:190`.

The scenario book should start each fixed contract at the common executable
mark, even if subsequent marks are generated by GROMM2. Training and live
features at the conditioning instant must use the same released state.

### 2. The executed claim-minus-zero hedge does not have the turnover objective that was trained

`hedger.py:95`--`hedger.py:130` fits the long, short, and zero books separately;
each virtual book is charged exact absolute turnover. `hedger.py:140`--
`hedger.py:159` then executes the difference between the long and zero actions.
Although the latest weekly adapter correctly carries three distinct virtual
books across restarted fits (`weekly_adapter.py:195`--`weekly_adapter.py:217` and
`weekly_adapter.py:289`--`weekly_adapter.py:312`), this does not resolve the
nonlinearity:

```text
cost((h_claim - h_zero) - (h_claim_prev - h_zero_prev))
    != cost(h_claim - h_claim_prev) +/- cost(h_zero - h_zero_prev).
```

The benchmark charges the realized cost of the net action, but neither fitted
objective optimizes that cost. Consequently the README/PLAN statement that the
reported claim-minus-zero hedge uses exact recurrent turnover is not true for
the executed hedge. Free settlement and terminal liquidation are correctly
implemented for each virtual book, but the same mismatch remains after those
operations. A coupled formulation or a separately optimized pure-hedge policy
is required if transaction costs are part of the benchmark objective.

### 3. The runtime does not enforce an accepted compatible physical drift

The public README describes scenarios under an "accepted compatible rolling P
drift". The rolling GROMM2 fitter actually calls the older
`quantdata/gromm2/estimation.py:801` estimator, and the only hard acceptance gate
in `rolling_gromm2.py:213`--`rolling_gromm2.py:229` is the affine market
inside-spread percentage. The dynamics loader accepts and uses the physical
risk-price coefficients without checking the validation-improvement,
validation-gain statistic, or daily risk-price norm used by the accepted Phase-4
physical-drift fit. The `selective_state_space.accepted` field in the GROMM2
report concerns a separate volatility-amplitude model and is neither a P-drift
acceptance criterion nor checked by the loader.

Existing scenario tests only compare P and Q when the risk-price coefficients
are exactly zero. They therefore do not demonstrate a genuine measure change or
its stability. P production must hard-reject an unaccepted physical fit and add
a deterministic nonzero-risk-price regression.

### 4. A rolling artifact is not tied back to the runtime public dataset

Preparation records `dataset_manifest_sha256` in
`rolling_gromm2.py:169`--`rolling_gromm2.py:185`, but
`_validate_prepared_manifest` (`rolling_gromm2.py:407`) does not compare that
field with the active dataset. The weekly adapter then discards its restricted
as-of panel at `weekly_adapter.py:145` and loads by artifact root, date, and
configuration only. Thus a complete artifact from another public-candidate
revision with the same dates and configuration can be silently paired with the
current execution panel. Internal file hashes prevent artifact corruption, but
not this source-identity mismatch.

The active public manifest identity must be supplied and checked on every daily
and weekly artifact load.

## Verified behavior

- Fixed-contract weekly strikes and price bridges are in episode-origin PV
  units. The bridge in `gromm2_weekly.py:530`--`gromm2_weekly.py:533`, combined
  with `current_scale`, gives the correct `D(0,T) F(t,T) / S(0)` normalization.
- Weekly spot gains, cash-settled option expiry, free settlement reset, and
  terminal liquidation have the correct array orientation and units.
- Buyer and seller price signs in `hedger.py:39`--`hedger.py:47` are correct for
  cash-invariant losses. Daily reporting correctly adds the GROMM2 Q model price
  back to the centered indifference adjustment in `adapter.py:301`--
  `adapter.py:307`; weekly prices are already full-payoff values and are divided
  by claim quantity and the fit-date PV scale.
- Frozen weekly policies replay the complete observed LSTM history, while
  restarted policies consume only the first action of the current dated refit
  and reject stale fits (`weekly_adapter.py:253`--`weekly_adapter.py:285`).
- Rolling artifacts contain exactly the configured trailing state count, end on
  the as-of date, reject future-dated states, and verify their internal hashes.
- The background 5% Black shock is unchanged between P and Q; the intended P
  change is confined to translated DLV/front Brownian factors.

## Test evidence and gaps

Focused CPU command: the six GROMM test modules passed **28 tests** in 17.89s;
Ruff passed on the implementation and focused tests. A direct synthetic check
also confirmed the initial weekly feature mismatch stated above.

Missing adversarial regressions correspond directly to the blockers:

1. equality of generated and live features at the initial weekly decision;
2. common executable entry marks in daily and weekly generated gains;
3. realized turnover of the executed claim-minus-zero action with nonzero,
   distinct component books;
4. a nonzero accepted P risk price producing a stable and measurably different
   distribution from Q; and
5. rejection of an artifact prepared from a different public manifest.

The advertised four-candidate architecture selection also still uses the older
`simulation.generate_gromm_daily_scenarios` path rather than the new 200-strike
rolling GROMM2 book (`selection.py:41`--`selection.py:43`). This is consistent
with PLAN.md saying managed-GPU architecture selection remains outstanding, but
the README should not present that selection as completed evidence for the new
integration until it has actually run on the production scenario semantics.
